2026年の原則

数年前の「必須MOD20選」を全部Subscribeするのではなく、今の互換性をSkyve等で確認してから入れます。

最初にVanilla Saveを一つ残す

MODを入れる前に正常起動とSave loadを確認します。Trouble時にVanillaで再現するかを切り分けられます。

Harmonyは依存基盤

多くのMODが必要とするFrameworkです。必要なMODが要求するVersionを確認し、似た名前の古いHarmonyを混在させません。

Skyveは「起動前の健康診断」

Subscription、Dependency、Compatibility、Asset管理を起動前に確認できるため、大量MOD環境ほど価値が上がります。

Move Itは景観だけではない

道路Node、建物、Propを細かく調整でき、都市設計を修正する時にも使えます。ただし移動した道路形状がTrafficにどう影響するかも確認します。

TM:PEは交通の自由度を増やす

Lane connector、Priority、Signal、Speedなどを制御できます。Vanillaの道路設計を理解せず全部手動設定すると、都市拡張時の保守が重くなります。

81 Tiles 2は大規模化の前にCompatibilityを見る

利用範囲を大きく増やすMODはSave全体へ影響します。既存Saveへ導入/削除する場合は作者説明とBackupを確認します。

Loading関連MODは現行後継を確認する

古いGuideには既に更新停止した名前が残ります。同じ目的の後継MODがあるか、Workshopの更新日とコメントを確認します。

同じ機能を二つ入れない

Traffic、Anarchy、Road toolなど役割が重なるMODは競合や設定混乱の原因です。目的ごとに主役を一つ決めます。

Asset数はMOD数とは別の負荷

Building/Prop/Vehicle Assetを大量にSubscribeするとMemoryとLoad timeが増えます。「MOD30個」より「Asset数千個」の方が重いこともあります。

メモリ不足の症状

Load途中で極端に遅い、Pagefileへ大量に逃げる、他Appが重くなる。16GB/32GBなど容量だけで断定せず、実際の使用量をMonitoringします。

新しいMODは一回の起動で少数だけ

10個同時に入れてCrashすると原因候補が10個になります。2〜3個ずつ追加し、毎回Saveを開いて確認します。

大型Update後は「何もしない」も正解

Game/Launcher/Workshop側が変わった日は、主要MODの対応を待つ方が安全なことがあります。動いているSaveを無理に開かない判断もあります。

Save Backupの最低運用

MOD追加前、MOD削除前、大型Update前の三つで別名Saveを残します。

MOD構成をProfile化する

景観用、軽量Play用、検証用など構成を分けると、全部入りを毎回使わずに済みます。

エラーが出た時の順番

  1. Vanilla/最小構成
  2. SkyveでConflict確認
  3. 直前追加を無効
  4. Dependency確認
  5. Logを見る

「必須MOD」は人によって違う

Trafficを深く触りたい人と景観制作をしたい人では必要なMODが違います。必須一覧を集めるより、自分の不満を解決するものだけ入れます。

SkyveでProfileを分ける理由

都市を遊ぶProfile、Map Editor、Asset制作、軽量検証を分けると不要MODのLoadを減らせます。一つの巨大Profileへ全部詰めない方がTrouble切り分けも楽です。

MOD削除は「Subscribe解除」だけで終わらない場合がある

設定FileやSave依存が残る場合があります。作者がSafe removal手順を案内しているなら従い、重要Saveを複製します。

Network Anarchy系の使いすぎ

自由な道路配置は可能になりますが、極端なNode距離や重なりがTraffic/描画で問題になることがあります。見た目だけでなくNetworkとして成立しているか確認します。

Node数とSegment数

大規模都市では道路を細かく分割しすぎるとGame limitやSimulation負荷へ近づきます。MODでMapを広げても内部上限が無限になるわけではありません。

Asset Missingは必ず致命的ではない

Prop等一部Asset欠落と、Network/Building dependency欠落では影響が違います。Loading reportやSkyve情報で何がMissingかを分けます。

道路AssetのDependency

Custom roadは別Network extensionやTextureを要求することがあります。道路を削除した後にSave内のSegmentが壊れる可能性もあるため慎重に整理します。

Theme/Visual MODをGameplay MODと分ける

LUT、Theme、Lightingなどは見た目中心。Traffic/Network/Simulation変更はGameplayへ影響。問題発生時にカテゴリを分けてDisableします。

FPS Booster系を魔法と思わない

改善する環境はありますが、巨大Asset数、CPU simulation bottleneck、RAM不足をすべて解決するわけではありません。

Pagefileを無効化しない

大量Asset環境ではMemory圧迫が大きく、Pagefileが最後の余裕になる場合があります。高速化目的で無効化するとLoad failureを増やす可能性があります。

Workshop CollectionをBackup代わりに使う注意

Collectionは一覧共有に便利ですが、作者がMODを削除・更新すれば同じBinaryを永久保存するものではありません。重要な構成は名称・Versionも記録します。

古いYouTube Guideの見分け

投稿日、Game最終Update前後、紹介MODの最終更新日、Commentの「broken」報告を確認します。導入操作は現行Workshopページを優先します。

MOD導入後に見る三つ

Main menuまで起動、Test cityをLoad、Console/Logに継続Errorがない。この三段階を通ってから重要Saveを開きます。

都市SaveとMOD Profileを一対にする

Save Aは景観MOD多め、Save Bは軽量など、どのSaveがどのProfileを前提にするか記録します。別Profileで誤って開く事故を減らせます。

Network系MODを外す前に道路をVanillaへ戻す

特殊NetworkやAnarchy状態へ依存している場合、MOD解除後に道路が壊れる可能性があります。作者のRemoval手順を確認します。

Theme Mixer系設定

Visual設定を保存しておかないと、同じSaveでも見た目が大きく変わります。Screenshot用PresetとPlay用を分けます。

Prop/Tree limitを意識する

Map拡張で土地が増えても内部Entity limitが無限になるわけではありません。景観都市ではAsset数と配置数を分けて考えます。

Simulation Speed低下

FPSは高いのにGame内時間が遅い場合、CPU simulation側が重い可能性があります。Graphic設定だけ下げても改善しにくいです。

FPS低下との違い

Cameraを動かした時だけ重いならGPU/描画、都市時間そのものが進まないならSimulationを疑います。

大量CitizenのPathfinding

都市規模とNetwork複雑化でCPU負荷が上がります。MODでTrafficを細かく制御するほど必ず軽くなるわけではありません。

Workshop Item削除への備え

作者がItemを非公開にすると再Downloadできない可能性があります。重要Saveは依存一覧を定期的に確認します。

Asset Collectionを用途別にする

日本風、欧州、工業、鉄道などCollectionを分け、一都市で使わないAssetまで全部Subscribeしない方がLoadを抑えられます。

Loading時Errorを無視し続けない

Playできるからと大量Errorを放置すると、後で原因が分からなくなります。新しく出たErrorから処理します。

MOD環境のスクリーンショットを残す

Skyve/Profile一覧を画像またはExportで残すと、PC移行時に復元しやすいです。

新PCへ移す時

Steam Workshopが再DownloadしてもLocal settingsやProfileが別にある場合があります。Saveだけでなく設定Folderも確認します。

2026年8月の前提

2026年8月時点：CS1向け81 Tiles 2は2026年にも更新実績があり、TM:PEも現行CS1向けRepositoryでSupportされています。

深掘り

2026年のMOD環境は「昔の有名MOD名」で選ばない

CS1は長寿命Gameなので、検索すると旧81 Tiles、古いLoading Screen系、旧Forkなどが大量に出ます。2026年のCommunityでも、旧81 Tilesではなく81 Tiles 2を使うよう案内するDiscussionが見られます。

MOD名が似ているだけで同じものだと思わず、作者、更新日、対応Game version、Dependency、後継MODを確認してください。特に古いBlogの「必須MOD10選」は、名前だけを今のWorkshopで探して入れるのが危険です。

深掘り

81 Tiles 2は『土地を増やすだけ』ではない

81 Tiles 2の公式Repositoryでは、Playable areaを81 tilesへ拡張することに加え、No pipes / No powerlinesなどの関連機能も説明されています。2026年5月にもv1.0.5の更新実績があります。

Map拡張は都市規模を広げますが、Simulation limitやCPU負荷を消すわけではありません。81 tilesを解放したから81 tiles全域を高密度化できる、と考えるより、景観・郊外・Network設計の自由度を増やすMODとして使う方が現実的です。

深掘り

TM:PEは最新版Game＋最新版MODの組み合わせを前提にする

TM:PE公式Repositoryは、最新のCities: Skylinesと最新のTM:PE v11 Stable/TestをSupport対象とし、古いGame/Mod versionはSupportしない方針を明示しています。

Traffic系MODはSaveへ深く関わるため、古いVersionをあえて固定するより、動いている環境をBackupしてから更新する方が長期運用しやすいです。Update後に問題が出た時は、TM:PEそのものだけでなくHarmony、Network系MOD、Node関連MODの競合も確認します。

深掘り

SkyveはCS1とCS2の情報を混ぜない

現在Web検索で『Skyve』を調べるとCities: Skylines II / PDX Mods向けSkyve情報も多く出ます。CS1の古い記事とCS2向け現行Siteを混ぜると、Install手順や対象Platformを誤解しやすくなります。

CS1ではCommunityの互換性情報や既存Playset管理Toolを使いつつ、どの記事がCS1向けかを必ず確認してください。特に「PDX Mods」という説明が中心ならCS2側情報の可能性があります。

深掘り

最小構成から増やす方が、最終的にMOD数を増やせる

Harmonyなど依存基盤→Loading/diagnostic→Move It/TM:PEなど中核QoL→Network/Building系→大量Assetの順に増やすと、どの段階で壊れたか分かります。

一度に50個Subscribeして起動できても、数日後にErrorが出た時に原因を特定できません。MOD環境は『何個入れられるか』より『壊れた時に戻せるか』が重要です。

深掘り

MODを外す時こそ、導入時より慎重にする

UI表示だけを変えるMODと、Road、Building、Node、Map tile、Simulationへ作用するMODでは、削除時の影響が違います。Subscribe解除できたから安全、とは限りません。既存SaveがそのMOD由来のNetworkや設定を参照している場合、次回Loadで別の問題として表面化することがあります。

削除前にSaveを複製し、対象MODの説明・Dependency・Uninstall注意を確認し、Test copyでLoadしてください。問題がなければ本番へ進めます。MOD環境を長く使うほど「入れる手順」だけでなく「戻す手順」を持つことが重要です。

最後に

この記事を実際のPlayへ落とす時の順番

  1. 現在のVersionを確認する。

    記事公開時点とGame内表示が違う場合は、数字やUI名より現在Versionを優先します。

  2. いま起きている問題を一つにする。

    資源・物流・MOD・Server・Trafficなど複数の問題が同時に見えても、最初に崩れた一箇所から直します。

  3. 変更前の状態を残す。

    Save、設定、MOD Profile、都市Layoutなど、戻れる状態を作ってから大きく変更します。

  4. 改善したか一つの指標で見る。

    変更を重ねる前に、元の問題が本当に小さくなったか確認します。

GameFinderでは、固定Build orderより「条件が変わっても使える判断」を重視しています。同じ攻略をそのまま再現するより、自分のSaveで何が不足しているかを読み替えて使ってください。

判断基準

MODは「便利そうだから全部入れる」より、役割で分けた方が壊れにくい。

UI改善、性能改善、操作補助、Content追加、Overhaulでは壊れ方が違います。まずQoL系だけで起動を確認し、その後に大型MODを追加すると、問題が起きた時に原因を戻しやすくなります。Version更新直後は『有名MODだから安全』ではなく、対応Versionと依存関係を確認する方が重要です。

失敗しやすいところ

一番避けたいのは、複数MODを同時更新して原因が分からなくなること。

Save互換、Loader、依存MOD、設定Fileのどこで壊れたのかを切り分けられない状態が最も復旧しにくいです。大型Update前はSaveと設定を分けてBackupし、変更は一段階ずつ行う方が安全です。
