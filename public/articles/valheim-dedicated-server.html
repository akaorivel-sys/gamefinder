友達サーバーの優先順位

24時間稼働より先にBackupとUpdate手順を決めます。

Dedicated Serverが必要な人

Hostがいない時間にも遊びたい、Worldを長期共有したい、常時同じ設定で運用したい場合に価値があります。全員が毎回同時に遊ぶなら普通のHostでも十分な場合があります。

自宅サーバーとVPS

自宅は追加月額を抑えやすい一方、PC稼働、家庭回線、Port、停電、Backupを自分で管理します。VPSは常時稼働しやすい代わりに月額とOS管理が必要です。

人数だけでRAMを決めない

4人でも大規模建築や探索範囲、MODで負荷は変わります。まず公式/Communityの目安から小さく始め、CPU/RAMを実測します。

World Backupを複数世代残す

最新Backup一個だけでは、破損に気づいた時点で正常な世代を上書きしている可能性があります。日次数世代＋大型Update前を別に残します。

Update前にServerを止める

接続中Playerがいないことを確認し、World save→Backup→Update→起動→接続Testの順で行います。

MOD ServerはVersion固定を意識する

Game本体だけUpdateしMODが未対応だと接続やWorldで問題が起きる場合があります。自動Updateを便利だからと無条件で使わず、対応状況を確認します。

Server Passwordだけでなく管理情報を分ける

Admin権限とPlayer用Passwordを同じように扱わず、管理できる人を限定します。

Worldを移転できる状態にする

VPSを変える、契約を止める時にWorld/Configを持ち出せるか確認します。独自Panelのボタンだけに依存しない方が長期では安心です。

Lagが出たら全員か一人かを見る

全員同時ならServer側、一人だけならそのClient/Network側の可能性が高い。問題範囲を最初に分けます。

大規模建築はNetworkとClientにも影響する

Server性能だけ上げても、巨大拠点を表示するClientが重い場合があります。Server lagとFPS低下を分けます。

Restartは根本対策ではない

定期Restartで一時的に改善しても、MOD/設定/World負荷が原因なら再発します。LogとMetricsを残します。

友達Serverの最小運用ルール

  1. 誰がAdminか
  2. Backup時刻
  3. Update日
  4. MOD一覧
  5. 問題時の連絡先

VPS Planを上げる時

CPU張り付き、RAM不足、Storage不足を実測してから変更します。人数だけで上位Planへ行かない方が費用を抑えられます。

半年後の再開を想定する

Game version、World、MOD list、Server start commandをTextで残すと、数か月休止後でも再構築できます。

World SaveとCharacter Saveを区別する

Server WorldとPlayer Characterは保存場所・扱いが異なるため、移転時に何を持ち出す必要があるか確認します。Worldだけ戻ってもCharacter側が想定と違う状態になることがあります。

Crossplay設定

利用PlatformやServer方式によってCrossplay関連設定が関係します。友達のPlatformを最初に確認し、公式Guideの現在手順を使います。

Port設定を必要以上に広げない

自宅Hostingでは公式が案内する必要Portだけを設定し、Routerの管理画面や他Serviceまで外部公開しません。

Server名とPassword

公開Listingを使うか、友達限定かで設定が変わります。Passwordは他Serviceと使い回さず、公開Chatへ貼り続けない方が安全です。

自動Backupだけに頼らない

大きなUpdate前やMOD追加前はManual backupを別名で作ります。自動Backupが破損後のWorldを上書き保存する可能性もあります。

Worldサイズと探索

長期Serverでは探索範囲が広がりSaveも変化します。Storage余裕を持ち、Backupの増加も見ます。

MODなし基準を作る

Serverが落ちる時、可能なら同じWorld/新規WorldをVanillaで確認し、Server software自体かMODかを分けます。

友達全員のMOD Versionを揃える

Thunderstore等Community managerを使う場合でも、Profile codeや一覧を共有し、個別に勝手なVersionへ更新しない運用が安定します。

性能不足とNetwork問題

敵AIやWorld updateが全員で遅いのか、特定Playerの移動だけRubber-bandするのかを比較します。

VPS Region

日本の友達中心なら日本/近隣Regionを優先し、海外メンバーがいるなら全員のPingを見ます。

Server Metricsを残す

人数、RAM、CPU、Save size、Restart頻度を月一回記録すると、長期化による変化を把握できます。

Serverを一時休止する時

World/Config/Mod listをArchiveし、再開時に必要なGame versionやCommandもTextで残します。

Server Start Commandを保存する

World名、Port、Password、Public/Crossplay等のOptionをTextに残します。再Install後に記憶で再構築しない方が安全です。

Windows ServiceやLinux systemd化

常時ServerではOS起動後に自動Startさせる方法がありますが、最初に手動Start/Stop/Backupを理解してからAutomationします。

Auto-restartの前に正常Shutdown

Process killではなくServerがSaveを完了できる方法で止めます。自動化Scriptを作る場合もGraceful shutdownを組み込みます。

BackupをServer内だけに置かない

同じDiskが故障すればWorldとBackupを同時に失います。定期的に別PC/StorageへCopyします。

Mod ManagerのProfile共有

Community toolを使う場合、全員へ同じProfileを配り、各自が個別追加するMODをClient-onlyへ限定します。

Server-sideとClient-side MODを区別

UI変更だけと、World/Item/Gameplayを変えるMODでは必要導入先が違います。作者説明を確認します。

Version mismatch時の順番

Game本体→Dedicated Server build→Framework→個別MODの順にVersionを比較します。全部再Installする前に差分を見ます。

World破損を疑う前に新規WorldでTest

同じServer binaryとMOD構成で新規Worldが動くなら、既存World側の問題範囲を狭められます。元Worldは上書きしません。

VPS SnapshotとGame Backupを別に持つ

SnapshotはOS全体復元に便利、World Backupは頻繁なGame復元に便利です。用途を分けます。

運用Documentを一枚作る

Start、Stop、Backup、Update、Restore、MOD profile、連絡先を一ページにまとめます。Server ownerが不在でも復旧できます。

Serverを強くするよりPlayer数を制限する判断

一時的なEventで人数が増えるだけなら、常時高額Planへせず最大人数を調整する方が合理的なこともあります。

長期Serverの「卒業」

遊ばなくなったら課金を続けず、Worldと設定をArchiveして停止します。再開時に戻せる状態なら、常時稼働させ続ける必要はありません。

Worldを戻す練習を一度だけしておく

Backupがあるだけでは十分ではありません。Test用WorldでBackupから復元し、Serverが起動してPlayerが接続できるところまで一度確認します。事故当日に初めてRestore手順を読むより、平常時に一度成功させておく方が安全です。

Server更新後の確認項目

起動Log、World load、Player接続、建築物、Portal、Boss progression、MOD機能を短時間で確認します。Serverが起動しただけで「更新成功」とせず、実際のWorldを一人で数分歩いてから全員へ開放します。

管理者が不在でも止められる状態

Server owner一人だけがRestartやBackupを知っていると、その人が不在の時に全員が待つことになります。信頼できる一人へ最低限の停止・起動・Backup確認手順を共有しておくと長期運用が楽です。

判断基準

MODは「便利そうだから全部入れる」より、役割で分けた方が壊れにくい。

UI改善、性能改善、操作補助、Content追加、Overhaulでは壊れ方が違います。まずQoL系だけで起動を確認し、その後に大型MODを追加すると、問題が起きた時に原因を戻しやすくなります。Version更新直後は『有名MODだから安全』ではなく、対応Versionと依存関係を確認する方が重要です。

失敗しやすいところ

一番避けたいのは、複数MODを同時更新して原因が分からなくなること。

Save互換、Loader、依存MOD、設定Fileのどこで壊れたのかを切り分けられない状態が最も復旧しにくいです。大型Update前はSaveと設定を分けてBackupし、変更は一段階ずつ行う方が安全です。
