Dedicated Serverにする理由

HostがGameを起動している間だけ遊ぶ方式と違い、Dedicated ServerはGame clientから独立して稼働できます。友達が別々の時間に入る、Worldを長期運用する、MOD構成を固定する場合に向きます。

運用は4層で分ける

Server本体SteamCMD / Build
→
設定INI / Sandbox
→
WorkshopMOD / Map
→
WorldSave / Backup

SteamCMDでServerを分離する

Community guideではValveのSteamCMDを使い、Project Zomboid Dedicated Server用AppをInstallする流れが紹介されています。Game clientとServer filesを分けると、ServerだけUpdate/Restartしやすくなります。

Server設定は「難易度」と「運用」を分ける

Zombie数、Loot、感染などGameplay設定と、Player数、Password、Public listing、RCONなど運用設定を一緒に変えると原因が追いにくくなります。まずVanilla相当で接続確認し、その後Sandboxを調整します。

Workshop MODはIDだけでなく読み込み側も見る

Project Zomboid ServerではWorkshop itemとGame内Mod IDが別に扱われる場面があります。古いGuideから数字だけコピーするのではなく、現在のWorkshop pageとMod descriptionでServer向け記述を確認します。

Map MODは途中追加を軽く考えない

Mapへ新Regionを追加するMODは、既に生成済みのWorld dataやLoad orderと関係します。新規Worldで試す方が簡単な場合があり、既存Serverへ追加するなら作者の導入順を確認します。

Update前Backup

Game update、Server build、Workshop updateが同じ日に起きると、Clientだけ更新済み、Serverだけ旧版、MODだけ旧版という組み合わせができます。Maintenance前にWorld/ConfigをBackupし、Update後に少人数で接続Testを行います。

友達用なら管理を複雑にしない

4〜8人程度のClosed Serverなら、公開Server向けの過剰なPlugin・Admin automationを最初から積む必要はありません。Password、Backup、Restart方法、MOD一覧、Versionを共有できれば十分なことも多いです。

友達用Serverの現実的な運用例

平日は夜だけ4人、週末は8人まで、MODは20個程度というServerなら、公開Serverのような複雑な管理機能より「毎日Backup」「Update前停止」「MOD一覧共有」「再起動方法」の四つを確実にする方が価値があります。Server ownerだけが全部知っている状態を避け、最低一人は復旧手順を共有します。

Serverを止めずにUpdateしない

Worldへ書き込み中にProcessを強制終了するとData破損Riskがあります。正常Shutdownを行い、Backupを取り、Server buildとWorkshop itemを更新し、起動後にLogを確認します。Playersが接続したまま自動Restartする運用なら事前通知も必要です。

MOD一覧をTextで保存

Workshop link、Workshop ID、Mod ID、Version/更新日を一覧にしておけば、新しいServerへ移行するとき再構築できます。Server configだけBackupしても、数か月後に同じMOD構成を再現できないと意味がありません。

Map MODの順番を固定する

複数Map MODが同じCellへ触る場合、Load orderやCompatibility patchが重要になります。作者が指定するMap orderを優先し、Server稼働後に頻繁に並び替えません。

Server Logを捨てない

接続失敗やMOD ErrorはPlayer画面よりServer logに詳しく残る場合があります。問題が起きた時刻、Player、直前Updateを記録し、該当時間帯のLogを保管します。

VPSへ移す判断

Host PCを毎晩起動するのが負担、回線やPort設定が不安定、友達が昼間も入りたい、といった運用問題が出てからVPSを検討できます。単に「専用ServerだからVPSが必要」ではありません。

Server restart前の最低チェック

接続中Playerがいないか、World saveが完了しているか、Backupが作成されたか、Update対象がGame本体かMODかを確認します。Restart理由を残しておくと、問題発生時に「最後に何を変えたか」が分かります。

Admin権限を全員に配らない

友達限定Serverでも、設定変更やItem spawnなどが可能なAdmin accountは必要な人だけにします。誤操作でWorldやGameplay balanceを変える可能性があるためです。普段遊ぶAccountと管理用権限を分ける方法もあります。

Connection問題はServerが落ちているとは限らない

一人だけ接続できない場合、Server全体よりClient version、Workshop download、Firewall、Account状態を疑います。全員が同時に入れない場合はServer process、Port、Update mismatchを優先します。

長期Worldほど定期的に別名Backup

同じBackup slotだけを上書きすると、破損に気づいた時点で正常世代も消えている可能性があります。日次数世代＋大きなUpdate前のManual backupを別名で残すと復旧範囲が広がります。

よくある疑問

Dedicated Serverは24時間PCをつける？

自宅HostならServer PCは稼働が必要です。VPSならService側で常時稼働できます。

SteamCMDはGame本体と別？

Dedicated Server filesをClientと分けてInstall/Updateするために使えます。

MODはClientだけでいい？

Server側にも必要なMODがあります。作者説明とServer設定を確認します。

Workshop IDとMod IDは同じ？

別に扱われる場合があります。数字だけでなくMod descriptionのServer設定例を確認します。

Map MODを途中追加できる？

可能なケースもありますが生成済みWorldとの関係が複雑です。Backupし、作者手順に従います。

Updateで入れなくなった？

Client、Server build、Workshop MODのVersionずれを順に確認します。

公開Server向け設定は必要？

友達限定なら不要な機能も多いです。最小構成から始めます。

BackupはWorldだけ？

ConfigやMod listも同時に残すと復元後の再現が簡単です。

読み終わったら確認すること

  1. この記事の手順をそのまま暗記せず、自分のSave・PC・Versionで条件が同じか確認する。
  2. 一度に複数の設定を変えず、一つ変更して症状や結果がどう変わったかを見る。
  3. 更新で変わる情報は公式ページや配布元の更新日を確認する。
  4. 失敗した場合は最後の操作だけでなく、その前に何が不足していたかまで戻って考える。

うまくいかない時は、答えを探す前に状態を保存する

Project Zomboid専用サーバー｜MODを入れる前に運用を決めるのように複数の要素が絡むテーマでは、設定を何度も変えているうちに「何を変えたら直ったのか」が分からなくなります。問題が起きた時点で、Version、設定、MOD一覧、PC構成、表示されたMessage、直前の変更を一度メモします。Saveや設定Fileを複製できる場合は、変更前の状態を残します。

次に、原因候補を大きなカテゴリへ分けます。Game本体、設定、追加MOD/Tool、Network、Hardware/性能、Save dataのどれかです。全部を同時に疑うのではなく、最小構成へ戻して一つずつ足していきます。この方法は特定のGameだけでなく、MOD、Server、配信、VR、StorageのTroubleshootingにも共通します。

検索結果を読むときは「同じVersionか」を最初に見る

検索上位の記事や高評価Commentでも、書かれた時点では正しくても現在は前提が変わっていることがあります。投稿日、最終更新日、Game version、Tool versionを確認し、一次情報と矛盾する場合は公式の現行仕様を優先します。GameFinderでも、Communityの意見は「どう感じる人が多いか」「どこで詰まりやすいか」を知る材料として使い、仕様そのものの根拠には公式資料を優先しています。

最適化は、問題を再現できるようになってから

効率やPerformanceを上げる前に、まず同じ条件で問題を再現できるか確認します。再現条件が分かれば、変更前後を比較できます。逆に一度しか起きない問題に十個の対策を同時に入れると、改善したように見えても原因は分かりません。専門的な設定ほど、一回の大きな変更より小さな検証を積み重ねる方が確実です。

2026年8月の前提

2026年8月時点：Build 42.20 Stableが標準。B41を継続する場合はlegacy41 branchを分離して扱います。

深掘り

Dedicated Serverを選ぶ前に、Persistent worldが本当に必要か決める

少人数でHostがいる時だけ遊ぶなら、In-game Hostの方が管理は簡単です。Dedicated Serverが必要になるのは、Host不在でもWorldを維持したい、別Machine/VPSへ負荷を分離したい、運用者を分けたい、といった理由がある時です。

『Dedicatedの方が本格的だから』だけで選ぶと、Update、Backup、Port、MOD同期、Log確認の仕事が増えます。先に人数、稼働時間、MOD数、誰が管理するかを決めてください。

深掘り

Buildを揃えることが、接続Troubleの第一条件

Build 42.20は2026年7月29日にStableへ入り、公式はB41 SaveがB42と互換ではないと案内しています。ServerとClientでBranchが違えば、設定を直しても接続問題は解決しません。

B41を残すGroupはlegacy41とB42 Stableを別Install/別Saveとして扱い、同じFolderへ混ぜない方が安全です。Update前にServerを停止し、SaveとConfigをBackupしてからFile更新を行います。

深掘り

MOD Serverは『Server側だけ入れる』では成立しない

Workshop Item ID、MOD ID、依存関係、Game BuildをServerとClientで揃える必要があります。大型Update直後はMOD作者側の対応時間もあるため、Vanilla Serverが起動・接続できる状態を先に作り、その後MODを少数ずつ戻す方が切り分けやすくなります。

接続不能になった時、PortとMODを同時に触ると原因が見えなくなります。Local接続→外部接続→MOD追加という順で段階を分けます。

深掘り

BackupはSaveだけではなくConfigとMOD一覧も残す

World SaveだけBackupしても、同じSandbox設定やWorkshop構成を再現できなければ復旧に時間がかかります。Server INI、Sandbox variables、MOD/Workshop一覧、Server versionを同じ日付で保存してください。

特にMapを変更するMODや大型Build移行では、更新後に問題が出てから旧Saveへ戻すだけでは足りない場合があります。動いていた環境そのものを復元できる形が理想です。

深掘り

VPS選びはPlayer上限ではなく実運用で決める

表記上の最大Player数だけでは必要性能は決まりません。Map規模、Zombie/Animal Simulation、MOD、接続人数、Backup圧縮などが同時に負荷を作ります。

小規模Groupなら、最初から最大枠を想定した高額Planより、CPU/RAM使用率とWorld Save sizeを見ながら増やせる構成が扱いやすいです。管理画面の使いやすさ、Snapshot/Backup、再起動、Console/Logへアクセスできるかも性能と同じくらい重要です。

最後に

この記事を実際のPlayへ落とす時の順番

  1. 現在のVersionを確認する。

    記事公開時点とGame内表示が違う場合は、数字やUI名より現在Versionを優先します。

  2. いま起きている問題を一つにする。

    資源・物流・MOD・Server・Trafficなど複数の問題が同時に見えても、最初に崩れた一箇所から直します。

  3. 変更前の状態を残す。

    Save、設定、MOD Profile、都市Layoutなど、戻れる状態を作ってから大きく変更します。

  4. 改善したか一つの指標で見る。

    変更を重ねる前に、元の問題が本当に小さくなったか確認します。

GameFinderでは、固定Build orderより「条件が変わっても使える判断」を重視しています。同じ攻略をそのまま再現するより、自分のSaveで何が不足しているかを読み替えて使ってください。

判断基準

MODは「便利そうだから全部入れる」より、役割で分けた方が壊れにくい。

UI改善、性能改善、操作補助、Content追加、Overhaulでは壊れ方が違います。まずQoL系だけで起動を確認し、その後に大型MODを追加すると、問題が起きた時に原因を戻しやすくなります。Version更新直後は『有名MODだから安全』ではなく、対応Versionと依存関係を確認する方が重要です。

失敗しやすいところ

一番避けたいのは、複数MODを同時更新して原因が分からなくなること。

Save互換、Loader、依存MOD、設定Fileのどこで壊れたのかを切り分けられない状態が最も復旧しにくいです。大型Update前はSaveと設定を分けてBackupし、変更は一段階ずつ行う方が安全です。
