容量はビットレート×時間でほぼ決まる

Constant bitrate相当で考えるなら、40Mbpsの映像は1秒あたり約5MB、1時間で約18GBです。80Mbpsなら約36GB/時。実際の可変BitrateやCodecで前後しますが、購入前の概算には十分使えます。

Gameと録画を同じSSDへ置く場合

高速NVMe SSDなら同時Read/Writeに余裕があることも多いですが、容量不足の方が現実的な問題です。Game library 1.5TB、録画素材1TB、空き20%を確保したいなら2TBでは窮屈です。

編集する素材はSSD、長期保管は別でもいい

Video editing中はRandom accessとTransfer speedが効くためSSDが快適です。編集完了後の元映像を何年も置くなら、大容量HDDやNASへ移す方がCost/TBを抑えられます。

NASはBackupそのものではない

RAIDでDisk故障に耐えられても、誤削除・Ransomware・NAS本体故障は別問題です。重要な完成動画やProjectは別媒体/別LocationにもCopyを持ちます。

1か月の容量例

40Mbpsで月30時間録画すると約540GB。80Mbpsなら約1.08TB。さらにProxy、Export、Cacheが増えるため、編集PC側には素材容量ぴったりではなく余裕を残します。

最初に削るのは古いGameか、録画か

再DownloadできるGame本体と、二度と撮れない録画素材は価値が違います。容量が足りないなら、再取得可能なものから整理する方が安全です。

実際の容量を三つの配信スタイルで計算する

1080p60を軽めに保存

20Mbpsなら1時間約9GB。月20時間で約180GBです。Game本体を1TB使っていても2TB SSDで運用できる可能性がありますが、編集CacheとExportを含めて空きを残します。

高画質録画

80Mbpsなら1時間約36GB。週10時間、月40時間なら約1.44TBです。この時点でGame libraryと同じSSDへ一年分を置くのは現実的ではありません。編集済み素材をHDD/NASへArchiveする流れが必要です。

長時間配信のLocal recording

毎日3時間を30日録画すれば90時間です。40Mbpsでも約1.62TB。保存期間を「直近一か月」「採用Clipだけ永久」などに分けないとStorageはすぐ埋まります。

Codecで同じ画質の必要Bitrateは変わる

H.264、HEVC、AV1などCodecによって圧縮効率と編集Compatibilityが異なります。新しいCodecは容量を抑えやすい場合がありますが、古い編集SoftwareやDeviceで扱いにくいことがあります。容量だけで選ばず、録画後のWorkflowまで確認します。

録画専用SSDを分ける利点

Game installやWindows updateでMain SSDの空きが急減しても、録画領域を確保できます。編集素材を一括で消す、交換する、別PCへ移す操作も簡単です。性能目的というより管理目的で分ける価値があります。

HDD Archiveの考え方

完成済み素材や過去配信の原本はSequential readが中心なのでHDDでも十分な場合があります。編集を再開する時だけSSDへCopyします。頻繁に編集するActive projectはSSD、触らないArchiveはHDD/NASと役割を分けます。

Backup対象を全部同じにしない

再DownloadできるGameはBackup優先度が低く、設定File・Save・録画素材・編集Projectは再取得できません。Storage不足時は「消しても戻せるか」で優先順位を決めます。

容量計算の式

概算GB/時 ≒ Mbps × 0.45。20Mbpsなら約9GB、40Mbpsなら約18GB、80Mbpsなら約36GBです。AudioやContainer overheadで少し増えますが、購入前の見積もりには使えます。

編集Cacheが想像以上に増える

動画編集SoftwareはOriginal footageだけでなく、Proxy、Preview render、Cache、Auto-saveを作ります。素材1TBだから1TB空ければ足りるとは限りません。Active project用SSDは素材量＋Cache＋Export分を見て余裕を取ります。

「永久保存」と「一時保存」を分ける

配信全編を永久保存する必要がなければ、30日だけ原本を保持し、Clip候補だけ別Folderへ移す運用ができます。これだけで必要Storageは大きく下がります。保存Ruleを決めずにHDDを買い足し続けるより効率的です。

外付けSSDの注意

USB規格、Cable、Enclosureの性能がSSD本体より遅い場合があります。長時間録画で接続が切れるとFile破損につながるため、録画用に使うなら安定したPort/Cableを使い、Sleep設定も確認します。

Backupは完成品を優先

何十時間ものRaw footageすべてをCloudへ複製するのが高Costなら、編集Project、Thumbnail素材、完成Export、重要Clipだけでも別媒体へ残します。失った時に作り直せないものから守ります。

容量だけでなく書き込み持続性能を見る

短いBenchmarkで高速でも、長時間連続WriteでCacheを使い切ると速度が落ちるSSDがあります。高Bitrate録画を何時間も行う場合、録画Bitrateより十分高い持続Write性能があるかReviewやメーカー仕様を確認します。

空き容量不足は録画失敗につながる

録画開始時に十分空いていても、長時間配信で途中からDisk fullになることがあります。OBS側の残容量Monitor、Windows通知、録画前チェックを習慣化します。数十GBしか余裕がない状態で長時間録画を始めない方が安全です。

素材Folderを日付とProjectで分ける

2026-08-26_game-title_rawのように日付・Game・用途をFolder名へ入れ、編集Projectと紐付けます。数TBの素材を一つのFolderへ置くと、削除判断やBackupが難しくなります。

NASへ移した後にChecksum/再生確認

重要素材を移動したら、File sizeや再生を確認してからLocal copyを消します。大量Copyの途中で失敗しているのに元を削除するとRecoveryできません。

年間容量を先に出す

月500GBなら一年で6TB。月1TBなら12TBです。毎月SSDを追加するより、保持期間を決める、Archive HDD/NASを使う、不要部分をCutするなどWorkflowを先に設計した方がCostを抑えられます。

よくある疑問

40Mbpsは1時間何GB？

概算で約18GBです。40÷8=5MB/s、×3600秒で約18,000MBです。

80Mbpsなら？

概算約36GB/時です。可変Bitrateでは内容によって前後します。

2TB SSDで足りる？

Game libraryと月間録画量によります。空き容量も必要なので計算して判断します。

録画はHDDでもいい？

録画Bitrateを安定してWriteできるHDDなら可能ですが、編集はSSDの方が快適な場合が多いです。

NASに直接録画？

Network速度・安定性・Software構成を確認します。まずLocal録画→後で移動する方が単純です。

RAIDがあればBackup不要？

不要にはなりません。誤削除やNAS本体故障には別Backupが必要です。

古い素材を消す基準は？

再取得可能なGame本体より、二度と撮れない素材を優先して残します。

空き容量はどれくらい残す？

SSD性能やUpdate作業を考え、常にぎりぎりまで埋めない方が運用しやすいです。

読み終わったら確認すること

  1. この記事の手順をそのまま暗記せず、自分のSave・PC・Versionで条件が同じか確認する。
  2. 一度に複数の設定を変えず、一つ変更して症状や結果がどう変わったかを見る。
  3. 更新で変わる情報は公式ページや配布元の更新日を確認する。
  4. 失敗した場合は最後の操作だけでなく、その前に何が不足していたかまで戻って考える。

うまくいかない時は、答えを探す前に状態を保存する

次に、原因候補を大きなカテゴリへ分けます。Game本体、設定、追加MOD/Tool、Network、Hardware/性能、Save dataのどれかです。全部を同時に疑うのではなく、最小構成へ戻して一つずつ足していきます。この方法は特定のGameだけでなく、MOD、Server、配信、VR、StorageのTroubleshootingにも共通します。

検索結果を読むときは「同じVersionか」を最初に見る

検索上位の記事や高評価Commentでも、書かれた時点では正しくても現在は前提が変わっていることがあります。投稿日、最終更新日、Game version、Tool versionを確認し、一次情報と矛盾する場合は公式の現行仕様を優先します。GameFinderでも、Communityの意見は「どう感じる人が多いか」「どこで詰まりやすいか」を知る材料として使い、仕様そのものの根拠には公式資料を優先しています。

最適化は、問題を再現できるようになってから

効率やPerformanceを上げる前に、まず同じ条件で問題を再現できるか確認します。再現条件が分かれば、変更前後を比較できます。逆に一度しか起きない問題に十個の対策を同時に入れると、改善したように見えても原因は分かりません。専門的な設定ほど、一回の大きな変更より小さな検証を積み重ねる方が確実です。
