Game serverの記事は「おすすめVPS」と「RAM○GB」の比較だけになりがちです。しかしDedicated serverはGameごとに負荷の出方が違い、同じGameでもVanilla、Modded、公開Serverで条件が変わります。契約前に一番役立つのは会社名のRankingではなく、自分のServerが何をするのかを言語化することです。

1. 登録人数ではなく同時接続人数

Discordに20人いても、毎晩同時に入るのが4人なら4人基準から考えます。逆に公開ServerはPeak時の人数を見ます。Playerが増えるとSimulation、Entity、Chunk、Network trafficが増えますが、増え方はGameで異なります。

2. MODは個数ではなく中身

UI変更30個と、大型Map・NPC・Automationを追加する30個は別物です。Project ZomboidのMap Mod、Minecraftの大型Modpack、ARK系の大量Entityなど、World/Simulationへ触るものはMemoryやCPU、Save sizeへ影響しやすい。

契約前に「使う予定のMOD名」「Server対応か」「依存Mod」「Game version」を表にします。Client-only ModまでServer RAM計算へ入れないようにします。

3. RAMを増やせば全部解決、ではない

Memory不足ならRAM増設は有効です。しかしGame serverの一部処理はCPUの特定Threadへ負荷が集中します。vCPU数が多くても、一つ一つのCore性能が低ければTick lagが残る場合があります。

VPSの比較ではvCPU数、CPU世代や説明、共有/専有、Storage種別を確認します。Marketing表の「○人推奨」は、自分のMOD構成まで保証する数字ではありません。

4. Backupは性能表より先に見る

Worldが壊れた、MOD updateでLoadできない、誤操作で建築を消した。こういうときに必要なのはCPUではなく昨日のSaveです。自動Backup頻度、保持世代、復元方法、手動Snapshotの有無を確認します。

Server本体と同じDiskに一つだけCopyしても、Disk障害へのBackupにはなりません。重要な長期Worldは別Storageへ定期Copyする運用も考えます。

5. Regionは全員の位置で決める

日本在住の友達だけならJapan regionが分かりやすい。海外Memberが混じるなら、全員のPingを見て中間を選ぶ場合があります。回線契約のGbpsは帯域であり、Latencyとは別です。

6. Game / Server / MODのUpdate方針

Clientが自動UpdateしたのにServerが旧Version、またはServerだけ最新になりMODが未対応。これだけで接続不能になります。自動更新を許すか、遊ぶ前に管理者がCompatibilityを確認して更新するか決めます。

Modded serverでは金曜夜の直前に大型Updateを入れない、という単純な運用ルールも価値があります。

7. 管理方法を自分の技術レベルに合わせる

Game template付きServiceはWeb panel中心で始めやすい。汎用VPSはSSH、Firewall、Service管理、Update、Backup scriptなどを自分で扱う代わりに自由度があります。「安いからLinux VPS」ではなく、Trouble時に自分で復旧できる範囲で選びます。

自宅ServerとVPS

余っているPCならHardware費を抑えられますが、電気、回線、Router設定、停電、24時間稼働、Public IP周辺を自分で管理します。VPSはその一部をDatacenter側へ移すものです。どちらが安いかは稼働時間と既存Hardwareで変わります。

契約前のチェックシート

  • 同時人数
  • GameとServer software
  • MOD/Plugin一覧
  • 必要StorageとWorld成長
  • Backup頻度
  • 希望Region
  • 管理者が触れる範囲
  • 月額上限

GameFinderのServer plannerはこの条件を整理する入口に使い、最終的な必要要件は各GameのServer docsと利用Serviceの現在の仕様で確認してください。

実測値からPlanを上げる判断

Serverが重いと感じたら、まず全員が同時に遅いのか、一人だけ遅いのかを分けます。全員が同時ならServer CPUやSimulation負荷、特定PlayerだけならNetwork routeやClient側Performanceの可能性が高い。Server monitoringでCPU、RAM、Disk、Networkを記録し、Lag時刻と照合します。

Memoryが70%程度で安定しているのに一Coreだけ常時上限なら、RAMを倍にしても改善しにくい。逆にMemoryが上限へ張り付きSwapが発生しているならRAM増加が候補です。数字を見てからPlanを変えます。

友達Serverで本当に必要な機能

4〜8人程度なら、Whitelist/Password、定期Backup、簡単なRestart、MOD一覧共有、Update前の通知があれば十分なことが多いです。公開Server向けの複雑な権限Pluginや監視Systemを最初から積むと、管理対象だけ増えます。

公開Serverでは運用が性能より大きくなる

知らないPlayerを受け入れるなら、荒らし、Account管理、Admin log、Ban、Backup、Rule、Moderatorなど「人」の管理が増えます。最大Player数を上げる前に、問題発生時に誰が対応するか決めます。

Serverを終了するときの持ち帰り

World、Config、Player data、MOD/Plugin list、必要ならDatabaseをDownloadしてから契約を止めます。Provider独自Panelの設定はScreenshotやExportも残します。数か月後に再開する時、同じ構成を再現できる状態が理想です。

価格比較の最終式

月額Plan＋Backup option＋追加Storage＋必要Traffic＋管理に使う自分の時間を総Costとして考えます。数百円安くても、毎週Troubleshootingに時間がかかるなら「安い」とは限りません。

自宅サーバーを選ぶ場合のHardware設計

余っているPCを使うなら、Gaming GPUは多くのDedicated Serverでは重要度が低く、CPU、RAM、Storage、Network、安定稼働が中心になります。GameによってはServer processが特定Threadへ偏るため、古い多Core CPUより新しい高IPC CPUが有利な場合があります。必要Specは必ず各Server softwareのDocsやCommunity実測と照合します。

StorageはWorld data自体が小さくても、Backupを複数世代残すと増えます。SSDはMap/Chunk accessやUpdate作業を快適にしますが、長期Backupは別HDD/NASへ逃がす構成も可能です。

家庭回線で見るUploadとCGNAT

Serverを外部公開する場合、Download速度よりUploadと外部から到達できるNetwork構成が重要です。ISPや契約によってはCGNAT等で一般的なPort forwardingがそのまま使えない場合があります。その場合は契約内容を確認し、無理に設定を変更するよりVPSや対応Serviceを選ぶ方が簡単です。

Serverを安全に公開する基本

必要なPortだけを開け、OSとServer softwareを更新し、管理Passwordを使い回さない。不要なServiceを外部公開しない。汎用VPSならSSH keyやFirewallを使い、管理PortをGame portと同じ感覚で全開放しません。Game Server運用は「Game設定」だけでなくInternetへ置くComputerの運用でもあります。

MOD Serverでは「安定版」を作る

毎日自動で全MODを最新版へするより、全員が問題なく遊べているVersion setを一度固定し、大型Update後にTest環境で確認してから本番へ反映する方が安定します。Version一覧を残しておけば、壊れた時に前の組み合わせへ戻れます。

VPSを選ぶ前の10項目

  1. 同時接続の最大人数
  2. VanillaかMODありか
  3. Game/Server version
  4. CPUの説明
  5. 必要RAM
  6. World＋Backup容量
  7. 日本または参加者に近いRegion
  8. Snapshot/Backup
  9. Data export
  10. 自分が扱える管理方法

「推奨○人」の表記をどう使うか

Providerの人数目安は入口として便利ですが、その数字がどのGame version、MODなし/あり、設定、CPU世代を前提にしているか分からない場合があります。最小PlanでTestできるなら実測し、負荷が見えてから一段上げる方が過剰契約を避けられます。

「安いサーバー」と「安く運用できるサーバー」は違う

月額だけを見れば最小プランが魅力的ですが、管理画面が分かりにくく、バックアップが手動で、障害時の復旧に毎回時間がかかるなら、遊ぶ時間を削って管理することになります。逆にLinuxやサーバー運用そのものを学びたいなら、その手間が価値になることもあります。料金表では見えない「自分が何時間管理に使うか」まで含めて選ぶと、必要以上に高いプランにも、扱いきれない安いプランにも寄りにくくなります。

契約前に一度、終了手順まで想像する

Worldを別VPSへ移す、数か月休止する、自宅サーバーへ戻す。そのときWorld、設定、Player data、MOD一覧を普通のファイルとして持ち出せるか確認します。始める時だけ簡単なサービスより、やめる時にもデータを手元へ戻せるサービスの方が長期運用では安心です。

最初の一週間は性能を上げず記録する

同時人数、CPU/RAM使用量、重くなった時刻、バックアップ所要時間、MOD追加日を簡単に残します。一週間分あれば「金曜夜だけ重い」「探索で新しい地域を生成するときだけCPUが跳ねる」「MOD追加後からRAMが増えた」といった傾向が見えます。そこで初めてプラン変更や設定調整を行えば、原因の分からないアップグレードを減らせます。

仕様は公式ストア・公式Documentを優先し、Steamレビュー集計やプレイヤー議論から実際につまずきやすい点を確認しています。コメントの寄せ集めではなく、複数の情報を照合してGameFinderの文章として再構成しています。

判断基準

MODは「便利そうだから全部入れる」より、役割で分けた方が壊れにくい。

UI改善、性能改善、操作補助、Content追加、Overhaulでは壊れ方が違います。まずQoL系だけで起動を確認し、その後に大型MODを追加すると、問題が起きた時に原因を戻しやすくなります。Version更新直後は『有名MODだから安全』ではなく、対応Versionと依存関係を確認する方が重要です。

失敗しやすいところ

一番避けたいのは、複数MODを同時更新して原因が分からなくなること。

Save互換、Loader、依存MOD、設定Fileのどこで壊れたのかを切り分けられない状態が最も復旧しにくいです。大型Update前はSaveと設定を分けてBackupし、変更は一段階ずつ行う方が安全です。

攻略情報は条件が違うと結論も変わります。この記事では固定の「正解手順」を押し付けるより、条件が変わっても使える判断基準を優先しています。特にUpdate直後、Experimental branch、MOD導入環境では、本文の数字やUI名より考え方を先に使ってください。
